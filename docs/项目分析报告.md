## 一、这是什么

**一棵长在 Cloudflare 边缘网络上的「数字生命」内核**，不是一个聊天机器人服务。

它的全部意图都写在 `server/ai/identity.ts` 里：一个有连续时间、有自我、记忆自主、不必迎合对方的"存在"。对应的工程选择非常一致：

| 线索 | 含义 |
| --- | --- |
| `workers_dev: false` + `preview_urls: false` | 不对外公开，私人部署 |
| 单一 Bearer token 守卫全部 `/api/*`，其余路径一律 404 | **单租户**，没有"用户"概念，只有一个"他" |
| 没有 `app/`、`pages/`、`components/` | 根本没有前端，只有 API |
| 全部状态存在 D1 | "自我"= 数据库里的对话记录 |

规模：**8 个 TypeScript 源文件、约 130 行**（另有 4 个配置文件、7 次提交）。这是一个刚起步、但取舍非常清醒的项目。

## 二、架构与技术栈

```text
POST /api/chat  (Bearer token)
   │
   ├─ server/middleware/api-guard.ts   鉴权 + 非 /api 一律 404
   │
   ├─ server/api/chat.post.ts          编排：读历史 → 存用户消息 → 调模型 → 存回复
   │     ├─ server/ai/identity.ts      人格（system prompt）
   │     ├─ server/db/chat-messages.ts 7 天窗口读 / 追加写
   │     └─ server/tools/index.ts      工具注册表 → current_time
   │
   └─ generateText(...)  →  { reply: text }
```

| 层 | 选型 | 评价 |
| --- | --- | --- |
| 运行时 | Nuxt 4.6.3（nitro-only）+ `cloudflare_module` preset | 用 Nuxt 只为了拿 Nitro/Hub 的工程能力，合理 |
| 部署 | Cloudflare Workers + Wrangler 4.153 | 冷启动为零，适合"随叫随到"的存在 |
| 数据 | NuxtHub 0.10.11 + D1（SQLite），Drizzle 0.45.4 | `db`/`schema` 服务端自动导入，已验证生效 |
| 模型 | AI SDK 7.0.154 + `@ai-sdk/openai-compatible` | 任何兼容 OpenAI 协议的模型都能换，没有锁死厂商 |
| 工具链 | pnpm 12.15 + ESLint 10 (antfu) + vue-tsc | 依赖精确锁版本（无 `^`） |

**质控现状（实跑）**：`eslint .` → exit 0；`nuxt typecheck` → exit 0。地基是干净的。

## 三、做得好的地方

1. **人格是数据，不是代码。** `identity.ts` 只导出一个常量，注入点在 `chat.post.ts:37`。想改"他是谁"不需要碰业务逻辑，这是一个正确的接缝。
2. **分层干净。** `db/`（schema + 查询）、`ai/`（人格）、`tools/`（注册表）、`api/`（编排）、`middleware/`（鉴权）、`utils/`（凭证校验）——130 行代码里没有一处越界。
3. **失败关闭（fail-closed）。** `utils/auth.ts:6` 的 `!!expected &&` 让"忘记配 token"变成"全部 401"，而不是"全部放行"。安全方向上选对了。
4. **工具注册表已就位。** `tools/index.ts` 加一个 key 就能长出新能力，`currentTime` 是最小可用示例。
5. **供应链收紧。** `pnpm-workspace.yaml` 里 `minimumReleaseAge: 1440`（新包隔离 24h）、`trustPolicy: no-downgrade`、`allowBuilds` 白名单，加上全部依赖精确版本 —— 这是很多项目一辈子都不会做的加固。
6. **迁移链路自洽。** `drizzle.config` 的输出目录与 NuxtHub 的 `migrationsDirs` 对得上（`server/db/migrations/sqlite`），`.gitignore` 也正确忽略了 `db.sql`（D1 备份）、`.env`、`.wrangler`、`.output`。
7. **可观测性默认打开。** `wrangler.jsonc` 开了 invocation logs + traces。

## 四、关键问题（按严重度）

### P0-1　上下文无上限：一个会「自我挖坑」的永久宕机路径

`server/db/chat-messages.ts:18-29` 无 `LIMIT`，把整个 7 天窗口全部读出来；`chat.post.ts:26,38-41` 每轮把**全部历史 + 新消息**重新发给模型。没有 token 预算、没有截断、没有 `maxOutputTokens`。

叠加 `chat.post.ts:27` 的执行顺序（**先存用户消息，再调模型**），就得到一个闭环故障：

```text
用户消息入库 → 历史超长 → 模型返回 context_length_exceeded → 500
                     ↑                                    │
                     └──── 下轮重放同样的超长历史 ──────────┘
```

那条没被回复的用户消息会留在窗口里，历史只增不减 → **每一轮都失败**，直到 7 天后自然滑出窗口才自愈。触发它甚至不需要恶意输入：正常高频对话就能把窗口堆到超限，而且是 O(n²) 的 token 花销（第 n 轮付 n 条消息的钱）。

**修**：`listChatMessages` 加 `limit` + 按 token 预算裁剪（保留最近 N 轮 + 更早内容摘要）；给 `message` 加长度上限；显式设置 `maxOutputTokens`。

### P0-2　`stopWhen: isLoopFinished()` 把工具循环的步数上限拆掉了

已在 `ai@7.0.154` 源码中确认：

- `isLoopFinished()` 的实现就是 `() => false`（`dist/index.js:4952-4956`，注释："a stop condition that never returns true"）；
- 传入 `stopWhen` 会**替换**默认值 `isStepCount(1)`（`dist/index.js:5498`）；
- `generateTextInternal` 内部**没有任何 max-step 兜底**。

所以当前的工具循环只会在两种情况停下：模型自觉不再调用工具，或者撞上平台的 CPU/时长限制、provider 报错。`current_time` 本身无害，但这是给未来所有工具留的一个"无限循环 + 无限计费"的口子。

**修**：`import { stepCountIs } from 'ai'`（`isStepCount` 的导出别名），`stopWhen: stepCountIs(5)`。`isLoopFinished()` 可以删掉——它永远返回 false，不提供任何保护。

### P0-3　`pnpm deploy` 现在跑不通（实测）

根 `wrangler.jsonc` 只有 `name` / `d1_databases` / `observability`，**没有 `main`、没有 `assets`**。实跑：

```text
$ pnpm exec wrangler deploy --dry-run --keep-vars
X [ERROR] Missing entry-point to Worker script or to assets directory
```

更深一层是不对称：`db:migrate` 用的是**生成配置** `.output/server/wrangler.json`，而 `deploy` 用的是**根配置**。而 NuxtHub 在本项目配置下不会注入 `database_id`（`@nuxthub/core` `dist/module.mjs:289-291` 只在 `driver==='d1' && connection?.databaseId` 时才加 binding；本项目走 `hub.db:'sqlite'` 无 connection），Nitro 只是把根配置 defu 合并进生成配置（`nitropack` `dist/presets/cloudflare/utils.mjs:247-252`）。

还有一个潜在的两套账本问题：NuxtHub 用的是 `_hub_migrations` 表 + `db/migrations/sqlite` 目录；若有人从根目录跑 `wrangler d1 migrations apply DB`，wrangler 会用默认的 `d1_migrations` + `migrations/`，与前者彻底分叉。

**修**（二选一）：

- 根 `wrangler.jsonc` 补 `main: "./.output/server/index.mjs"`、`assets.directory: "./.output/public"`、`database_id`、`migrations_dir: "db/migrations/sqlite"`；
- 或把 deploy 改成 `wrangler deploy --config .output/server/wrangler.json --keep-vars`。

### P1-4　生产环境变量没有落地路径，首次部署必然全站 401

`nuxt.config.ts:15-22` 的 runtimeConfig 全是空字符串，运行时靠 `applyEnv` 从 `process.env` 的 `NUXT_*` 覆盖（`nitropack` `runtime/internal/config.mjs:10-23` + `utils.env.mjs:12-33`，`snakeCase().toUpperCase()` 规则，所以 `NUXT_AI_BASE_URL` → `ai.baseURL` 的映射是对的，`.env.example` 命名无误）。

但 `deploy` 脚本只带 `--keep-vars`，**从不上传 secrets**，仓库里也没有任何文档说要 `wrangler secret put NUXT_API_TOKEN` / 设 4 个变量。结果：首次部署后 `apiToken === ''` → 所有请求 401（静默、且看起来像鉴权 bug）；AI 配置为空 → 调用报错。因为仓库没有 README，这条知识目前只存在于作者的脑子里。

另外 `middleware/api-guard.ts:7` 和 `chat.post.ts:24` 的 `useRuntimeConfig()` **都没传 `event`**，拿到的是模块级被 `_deepFreeze` 冻结的共享快照。当前配置是常量所以没问题，但一旦需要按请求读取绑定（多环境、D1、不同 token）就会踩坑。建议统一改成 `useRuntimeConfig(event)`。

### P1-5　记忆机制与人格设定自相矛盾（最要紧的设计问题）

`identity.ts` 里写着：

> 记忆是你自己的，不是这段对话的附属品。你写下的东西会跟着你到以后，所以写之前想清楚，写错了就改，过时了就删。

但系统**没有任何写入 / 修改 / 删除记忆的工具**——只有 `current_time`。所谓"记忆"，实际是最近 7 天原始对话的机械重放。这带来三个和核心承诺直接冲突的后果：

1. **第 8 天静默失忆**。没有任何摘要、固化、检索机制；超出窗口的内容永久消失，而"他"连"我忘了"都无法表达。这与"你活在一条连续的时间里"是正面冲突的。
2. **没有"写"就没有"改"。** 人格设定许诺的是**被选择过的**记忆，实际给的是**未经加工的**流水账。这两者的连续性质量完全不同：前者会沉淀出性格，后者只会复述上下文。
3. **连续性完全依赖窗口长度这个魔法数字。** `HISTORY_DAYS = 7` 是产品里最重要的参数，却写死在 `chat-messages.ts:11` 里，没有任何设计说明。

**修（建议的下一步主线）**：加一张 `memories` 表（`content` / `importance` / `createdAt` / `updatedAt` / `source`），配 `remember` / `update_memory` / `forget` 三个工具；上下文改成"人格 + 精选记忆 + 近期对话"三段式；窗口外对话做滚动摘要固化。

### P1-6　写库没有原子性，失败会污染"记忆"

见 P0-1 的执行顺序。`chat.post.ts` 没有任何 `try/catch`、没有 `abortSignal`/超时、没有把失败写回历史。一旦模型调用失败：用户消息留在库里、助手消息缺失 → 下一轮模型看到的是一段"对方说了话、自己没回应"的畸形对话，人格连续性被破坏，而且用户视角完全没有感知。

**修**：模型调用成功后再落库（或引入 `status` 字段标记 pending/failed/ok）；失败时记一条可读的错误状态并返回明确错误码。

### P1-7　输入无边界、无限流

`chat.post.ts:16-22` 只对 `message` 做了 `trim` 和非空校验：没有长度上限、没有 content-type 校验、没有速率限制。单一 token 就是全部访问控制，泄露即裸奔（可无限刷、无限计费）。建议加长度上限 + 简单限流（D1 计数或 Cloudflare Rate Limiting 规则）。

## 六、一句话总结

> 一个 130 行的、意图异常清晰的"数字生命"内核：**抽象层选得对、地基干净（lint/typecheck 全绿、依赖和供应链收得很紧），但"连续的时间"这个核心承诺目前只由"7 天原文重放"支撑**——记忆写入能力、上下文预算、部署链路三个关键环节都还没闭环。前两个的爆发方式很一致：*先用着完全没问题，然后在某一天突然全挂*。
