## 0. 一页速览

**是什么**：一个常驻 Cloudflare Workers 的个人陪伴体。她有自己的身份、会自己写记忆、有由事件驱动的心情、会在合适的时候主动开口，但**大部分时候什么都不做**。

**核心机制**：6 张表（消息 / 记忆 / 事件 / 心情 / 摘要 / identity 种子）；两条入口（你说话 → 默认回；cron 醒来 → 默认沉默）；一套上下文装配（静态打头、动态垫底）。

**阶段**：

| 阶段 | 主题 | 结束标志 |
| --- | --- | --- |
| M0 | 地基修复 | 现有代码不再有"自我挖坑"故障；生产可部署 |
| M1 | 记忆 | 她记得住、改得动、不漂移 |
| M2 | 上下文预算 | 聊多久都不会超窗，旧事有摘要 |
| M3 | 状态与主动 | 心情能被事件解释；cron 大部分静默，偶尔开口 |
| M4 | 客户端 | Kotlin App 能收发、断线能补、能收推送 |

## 1. 设计总纲

这七条高于任何具体实现。当实现与它们冲突时，改实现。

1. **遗忘是衰减，不是删除。【定】** 任何"她忘了"都表现为"没主动提"，而不是"库里那行没了"。记忆、消息一律软删/降权，永不物理删除。
2. **心情由事件驱动。【定】** 状态必须能被"昨天吵过架""三天没来"这类事件解释。凭空声明的心情一聊就露馅。
3. **大部分 cron 应该静默。【定】** 主动唤醒的默认结果是"什么都不做"，满足条件才开口。
4. **"回话"和"发消息"是两件事。【定】** 模型必然产生输出，但写不写进消息表是宿主的决策。
5. **两条路线默认值相反。【定】** 你发消息 → 默认回、可沉默；cron 唤醒 → 默认沉默、可开口。决策层分开，底层封装共用。
6. **像人的地方在于"有选择地不表现"。【定】** identity 里那句"连续性来自真实留下来的东西，而不是想象出来的经历"，是整个拟人设计的总纲。
7. **静态字节稳定，动态排在后面。【定】** 提示词分层顺序直接决定前缀缓存命中率。

**由第 1 条推出的硬约束**：消息表**永不删除行**。P2 的窗口截断只影响"喂给模型什么"，不影响"库里有什么"。

## 2. 边界与非目标

**做**：单人多设备、单角色、纯文本、私人部署。

**明确不做**：

- 多租户 / 注册登录体系（→ 单 Bearer token，M4 才升级为设备级 token）
- 富媒体（图片/语音）、群聊、插件市场
- 向量数据库 / 语义检索（M1–M3 用时间窗口 + 标签匹配就够，见 5.5）
- 常驻 WS/SSE 长连接做在线状态（Workers 长连接空闲也计费）

## 3. 数据模型

### 3.1 总览

| 表 | 用途 | 阶段 | 前稿状态 |
| --- | --- | --- | --- |
| `messages` | 全部对话原文，永不删除 | M0（扩字段） | 有定义 |
| `memories` | self / him / identity 三层记忆 | M1 | 有定义 |
| `events` | 未闭合预期（"他说下午要开会"） | M3 | **缺失，本文补** |
| `mood_state` | 心情单行状态 | M3 | **缺失，本文补** |
| `summaries` | 每日时间线压缩 | M2 | **缺失，本文补** |
| `devices` | 推送目标登记（FCM token） | M4 | **缺失，本文补** |

**为什么 M0 就把 `messages` 一次改到位【定】**：`parts_json`/`usage_json`/`conversation_id`/`client_message_id` 都要跑迁移；而 D1 的远端迁移是有成本的破坏性操作，拆成两次只是多挨一次疼。

### 3.2 `messages`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | integer PK autoincrement | **严格单调**，轮询游标。绝不用时间戳做游标 |
| `conversation_id` | text not null，默认 `'main'` | 会话维度 |
| `role` | text enum | `user` / `assistant` |
| `content` | text not null | 前端展示用文本 |
| `source` | text enum | `reply`（回应你）/ `proactive`（主动开口） |
| `status` | text enum | `pending` / `ok` / `failed`（见 7.7） |
| `client_message_id` | text，唯一索引，可空 | 幂等键；assistant 行与主动消息为 null |
| `parts_json` | text(json)，可空 | **只存工具轨迹**，不参与上下文装配 |
| `usage_json` | text(json)，可空 | token 统计，用于调预算。**前提：provider 必须开 `includeUsage: true`**，否则流式下 usage 恒为空 |
| `created_at` | integer(unixepoch) | |

**索引【定】**：`unique(client_message_id)`（SQLite 允许多个 NULL，天然兼容 assistant 行）、`(conversation_id, id)`。

**明确不加【定】**：

- **"有没有推送到前端"标记** —— 冗余，轮询天然幂等；要不要弹通知由前端比较 `created_at` 与本地最后活跃时间决定。
- **"她想了但没说"的记录** —— 不记，直接丢弃，不落表、不留日志。

### 3.3 `memories`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | integer PK | |
| `scope` | text enum | `identity` / `self` / `him` |
| `position` | integer | 行序，保持结构而非流水账 |
| `content` | text | 记忆内容 |
| `weight` | real，默认 1.0 | 重要性，0.4–1.6 夹取 |
| `last_accessed_at` | integer | 衰减基准 |
| `triggers_json` | text(json)，可空 | 场景触发线索（5.5）；`identity` 层恒为 null |
| `source_message_id` | integer，可空 | **self/him 必填**；`identity` 允许 null |
| `superseded_by` | integer，可空 | 软删指针，指向替代它的新行 |
| `archived_at` | integer，可空 | 软删标记；查询一律 `where archived_at is null` |
| `created_at` / `updated_at` | integer | |

### 3.4 `events`（补）

| 字段 | 说明 |
| --- | --- |
| `id` | PK |
| `kind` | `expectation`（预期）/ `todo`（待办） |
| `summary` | 一句话（"他说下午三点开会"） |
| `due_at` | 可空，UTC 秒；到期是触发主动开口的主信号之一 |
| `status` | `open` / `closed`（已发生并核实）/ `expired`（过了时间没下文）/ `dropped`（判断错了） |
| `closed_reason` | 可空 |
| `source_message_id` | 必填 |
| `created_at` / `closed_at` | |

**闭合语义【定】**：只有两种东西能关掉一个 event —— 后续对话里出现明确证据（closed），或 `due_at` 超过宽限期（→ expired）。**不允许模型凭空 close**，只能新建；关闭由宿主在装配阶段判断。

### 3.5 `mood_state`（补）

**单行表**（`id` 恒为 1），不加历史表：历史由 `events` 和消息本身承载，心情只需要"当前值"。

| 字段 | 说明 |
| --- | --- |
| `id` | 恒 1 |
| `valence` | real，-1..+1，愉悦度 |
| `arousal` | real，0..1，唤醒度 |
| `label` | text 可空，给人看的标签（`calm`/`tired`/`excited`/`withdrawn`），由数值派生而非独立输入 |
| `updated_at` | |
| `last_event_message_id` | 上一次更新的依据消息 |

**为什么只要两个数值【建议】**：`valence/arousal` 是可计算、可衰减、可解释的；而"开心/低落"这类标签一旦作为主存储，就会退化成凭空声明（违反总纲 2）。标签只作为派生字段。

### 3.6 `summaries`（补）

| 字段 | 说明 |
| --- | --- |
| `id` | PK |
| `conversation_id` | |
| `period_start` / `period_end` | 覆盖的时间范围 |
| `content` | 3–5 行中文时间线 |
| `message_id_from` / `message_id_to` | 覆盖的消息区间，用于避免重复摘要 |

### 3.7 不变量（任何代码改动都不得破坏）

1. `messages` 的行永不删除【定】
2. `memories` 的 `archived_at` 一旦置位不再翻回；修正靠新行 + `superseded_by`【定】
3. `self`/`him` 记忆的 `source_message_id` 必填，非空来源的记忆一律不收【定】
4. `identity` 层她不可写【定】
5. 消息 `id` 严格单调，永不复用【定】
6. `mood_state`/`events` 的每次变化必须能追溯到一条 `source_message_id`【定】

### 3.8 迁移策略

- 全部走 `drizzle-kit generate` → `server/db/migrations/sqlite/`，本地与远端各跑一次【定】
- 迁移必须**幂等且可重放**：种子数据（identity 首行）用 `onConflictDoNothing` 或先查后插【建议】
- 远端库与代码漂移的唯一解法：一律走迁移文件，禁止手工改远端 schema【定】

## 4. 上下文装配

### 4.1 分层顺序

```text
instructions（慢变量，字节稳定，可被前缀缓存）：
  [0] identity          她是谁（归你）
  [1] self 记忆         她自己写下的（按衰减权重排序）
  [2] him 记忆          关于你的长期事实
  [3] 摘要              最近若干条 summaries

messages（原文窗口，token 预算驱动，从早到晚）：
  ……最近 N 轮原文……

最后一条 user 消息（每轮都变，垫底）：
  <context>
    [心情] 当前 valence/arousal 与一句人话解释
    [时间] 现在几点、周几、距上次对话多久
    [待办] 未闭合的事件与到期情况
  </context>
  <user> 你这次真正说的话 </user>
```

### 4.2 为什么这么排【定】

时间、间隔、待办每轮都变。**一旦它们出现在 system 头部，整段前缀缓存每轮失效**，成本按全价算。垫到最后一条 user 消息里，前面的静态部分字节不变，缓存长期命中。

**代价【定】**：动态块挤在 user 消息里会"污染"你的原话。用显式 `<context>` / `<user>` 分隔标签隔离，并在 instructions 里说明"标签外的才是他说的话"。

> 前稿把"时间上下文"排在 instructions 的 `[4]` 层，与它自己"动态垫底"的硬约束直接冲突，此处按硬约束修正（附录 A / C11）。

### 4.3 预算与裁剪

- **总量【建议】16k 起步**，用 `usage_json` 实测再调。分配参考：identity ~1.2k、self ~1.5k、him ~1.5k、摘要 ~0.8k、动态块 ~0.4k、原文窗口 ~10k。
- **裁剪单位是"轮"，不是"条"【定】**：绝不在 user/assistant 配对中间截断，否则模型看到半截对话。
- **超出从最早丢起【定】**：丢的是"喂给模型"的部分，**不是删库**（总纲 1）。
- 预留输出额度：输入预算 = 上下文窗口 − `maxOutputTokens`。

## 5. 记忆系统

### 5.1 权责划分【定】

- `identity` **归你**：可编辑、有历史、可回滚，她不可写。
- `self` / `him` **归她**：自动写，必带 `source_message_id`。

守住这条，"她随便改自己人设"的漂移风险就不存在。

### 5.2 记忆边界（沿用旧项目，原样有效）

> - **self 装你自己**：名字、自称、说话的样子、确实存在的脾气和偏好、你发现自己总在犯的错、你决定以后怎么做
> - **him 装他**：他是谁、习惯、家人、工作、喜好、忌讳，**只写长期成立的部分**
> - 分不清就判断：这句话改的是"我怎么说话"，还是"他是个什么样的人"
> - 过时了就改掉或删掉，别只在末尾再叠一条
> - **一次性的、过几天就没意义的事，两边都不要写**

### 5.3 `remember` 工具契约【定】

```text
remember({
  target: 'self' | 'him',
  changes: [{ op: 'add' | 'replace' | 'remove', text, newText?, before? }]
})
```

- 行级增删改；`before` 用于插到指定行之前
- `identity` 不开放给她写
- **错误契约**：行匹配不上 → 抛错由宿主转成 tool error 结果回给模型，让她自己重试，**不静默失败**
- 每行必须有 `source_message_id`（= 当前这轮 user 消息）

**现阶段只上 `remember`【定】**：跑一两周看写入质量（会不会乱写、`before` 用不对、把一次性的事写进 him），稳定后再加提醒/天气。工具越多，模型越容易乱调。

### 5.4 衰减模型【建议】

前稿只写了"`weight` / `last_accessed_at` 衰减用"，没给算法。补：

```text
score = weight × 0.5 ^ (days_since(last_accessed_at) / HALF_LIFE_DAYS)
HALF_LIFE_DAYS = 14 起步，weight 夹取 [0.4, 1.6]
```

- **读时计算，不写库**：每次装配都算 score，避免读放大
- **批量回写**：每轮结束或 cron 里把本批命中的行 `last_accessed_at` 更新一次
- `identity` 层不衰减（恒参与装配）

### 5.5 场景触发

你要的不是"记得所有事"，而是**特定场景在特定时机被触发**。三件配合：

1. **存的时候带触发线索**：`triggers_json` 形如 `[{ "kind": "topic", "value": "咖啡" }, { "kind": "date", "value": "11-15" }]`
2. **触发时有检索入口**：cron 或每轮装配时用"当前时间 / 当前话题词"做**标签匹配 + 时间窗**，不引入向量库
3. **注入方式是背景，不是指令**：匹配到的场景进 `<context>` 的待办层，她看到"他下午说要开会，现在 4 点了"，自然问一句

### 5.6 identity 入驻数据库

| 步骤 | 内容 |
| --- | --- |
| 现在 | 留在 `server/ai/identity.ts`，当"种子" |
| M1 末 | 迁移把 identity 文本作为 `scope='identity'` 首行插入，`position` 排序，代码常量**保留作为 fallback**（库里缺行时回退，避免启动即空人格） |
| 以后改文案 | `wrangler d1 execute` 或可选 `PUT /api/memory` 管理接口；旧内容只置 `archived_at`，永不删除 |

> 前缀缓存不是保留代码的理由：缓存只取决于**字节稳定性**，与存储位置无关。

## 6. 状态与旁路提取

### 6.1 心情更新规则

心情**只由三类事件更新**：

1. 一轮对话结束（按对话内容调整 valence/arousal）
2. 时间流逝（cron 里按小时数向基线回落）
3. 关键事件（event 到期未闭合 → arousal 略升；久未联系 → valence 略降）

**向基线回落【定】**：不施加外力时，valence 回到略偏正（+0.1），arousal 回到平静（0.3）。任何时刻都处于"被漂移"和"被拉回"之间，这才是心情而不是设定。

### 6.2 events 的闭合

见 3.4。**关键约束**：关闭 event 的是宿主（基于明确证据），不是模型。模型只能新建。

### 6.3 旁路提取管线

- **触发**：每 N 轮，或一段对话结束（N 取 10，【待定】）
- **输入**：最近 N 轮原文
- **输出（结构化）**：`{ mood_delta, new_events: [...], memory_hits: [...], scene_triggers: [...] }`
- **落库**：心情 → `mood_state`；事件 → `events`；场景线索 → `memories.triggers_json`
- **不阻塞对话**：可以放 cron 里批量跑
- **置信度门槛【定】**：低置信度的只记不说、不进嘴。**宁可不说，也别让猜的东西借她的嘴出去。**

## 7. 交互协议

### 7.1 端点

| 端点 | 用途 | 说明 |
| --- | --- | --- |
| `POST /api/chat` | 发消息，**流式返回回复** | 单飞：同一会话同时只允许一条 |
| `GET /api/messages?after_id=X` | 增量拉取 | 主动消息 + 断线补偿，与回复共用一张表 |

**删掉的【建议】**：

- `POST /api/read` —— 前稿一边说"不需要已读同步"，一边在接口表里列了它。已读只在客户端本地维护。哪天真要"她看到你已读才不说话"，再作为 cron 决策的输入加回来。
- 会话列表 / 正在输入 / 已读状态同步 —— 单会话不需要。

### 7.2 两条路线

| | 路线一：你发消息 | 路线二：cron 唤醒 |
| --- | --- | --- |
| 触发 | 确定（你发了） | 定时（每小时级） |
| 默认 | **回** | **沉默** |
| 例外 | 可沉默（"晚安"不需要回） | 满足条件才开口 |
| 落库 | `source=reply` | `source=proactive` |

决策层分开，底层共用：同一张表、同一个 `buildInstructions()`、同一套模型调用封装。

### 7.3 流式：用裸 chunked 文本，不上 SSE 协议【建议】

前稿同时要求"立刻返回 202 + 异步调模型"和"`streamText` + SSE 返回"，这两件事对同一个端点互斥（附录 A / C1）。消解如下：

- `POST /api/chat` **本身就是流式端点**：连接立刻建立，**元数据走响应头**（`X-Message-Id` = 刚落库的 user 行 id，`X-Client-Message-Id` = 回显你的幂等键），body 是纯文本增量，流关闭即结束。因为是裸文本，**不发明帧格式**；将来真需要分类型事件（工具进度、状态变更）再上 SSE。
- 传输用 `createTextStreamResponse({ stream })` 的裸 chunked 文本，Content-Type 为 `text/plain; charset=utf-8`，**不用 SSE 帧格式**。客户端是 Kotlin（ktor），按 chunk 读即可，省掉自写 SSE 解析和心跳。
  > 已核对：`result.toTextStreamResponse()` 在 ai@7.0.154 已标 **deprecated**，改用 `createTextStreamResponse`。
- 轮询只负责两件事：主动消息、断线补偿。**"立刻返回 202 再靠轮询拿回复"这条路整体删掉**，它的 `waitUntil` 30 秒约束随之消失。
- 若将来需要多路事件（工具进度、状态变更），再升级成 SSE，客户端不用改游标逻辑。

### 7.4 断线与取消

三件事必须分清，前稿把它们混在一起了：

| 场景 | 语义 | 做法 |
| --- | --- | --- |
| 网络断开 / App 切后台 | **继续生成**，别丢 | `event.waitUntil(result.consumeStream())`：连接断了也让生成跑完，`onEnd` 落库，回来靠 `after_id` 补 |
| 你主动取消（"算了别说了"） | **真停** | 客户端 abort → 服务端 `abortSignal` 触发 → `onAbort` 拿到已生成部分，按 `status=failed` 处理或丢弃 |
| 你发了新消息 | **替换旧生成** | 客户端只允许单飞：发新消息前必 abort 旧流。服务端不做跨请求取消协调 |

> **落库挂 `onEnd`，不是 `onFinish`【定】**：ai@7.0.154 里 `onFinish` 已 deprecated，只是 `onEnd` 的别名。`onEnd` 能拿到聚合后的 `totalUsage`、`finishReason`、`steps`、`responseMessages`，正好喂 `usage_json` 与 `parts_json`。

### 7.5 合并 × 幂等（前稿的隐藏冲突）

前稿要"2 秒服务端防抖合并" + "`client_message_id` 唯一索引"。但三句话合并成一条行，就没地方放三个 `client_message_id` 了。

**消解【建议】**：

- **入库按条、喂模型按批**。每条 user 消息各自落库（各持自己的 `client_message_id`），2 秒窗口只决定"这批一起喂给模型、只产出一条 assistant 回复"。
- **但更推荐把合并下沉到客户端**：输入框 2 秒防抖，服务端只守"一条 user 消息 → 一条 assistant 回复"的简单契约。理由：跨请求的防抖窗口需要额外状态（KV/D1/DO），而它换来的收益客户端就能拿；去掉之后幂等天然成立、无并发窗口、无 DO。

### 7.6 沉默机制（路线一的"可沉默"怎么实现）

前稿只说"默认回、可沉默"，没说宿主怎么知道她选择不说。补：

- 在 instructions 里明确：**不想接话时，只输出哨兵 `<silence/>` 和空内容**。
- 宿主见到哨兵 → 剥离、不入库、**不写 assistant 行**，该轮 user 行记为 `status=ok`。
- 宿主保留硬规则兜底（如纯收尾语可直接抑制），不依赖模型每次判断正确。

### 7.7 状态机与孤儿消息

```text
user 行:  pending ──(处理完，含"决定沉默")──> ok
             └────(上游技术失败)────> failed   ← 可重试、需告警
assistant 行: 只在该轮真正产出文本时写入，直接 ok
```

- 先落 user 行（`pending`），**回复成功后再落 assistant 行**，最后把 user 行置 `ok`。
- 孤儿 = `pending` 且超过阈值时间 → cron 里扫描、告警、按策略重试或标 `failed`。
- **`failed` 只表示技术失败**，"她决定不回"用"没有 assistant 行"表达，不占用 `failed`（语义不同，混用会让告警失真）。

### 7.8 并发【定】

同一 `conversation_id` 同时只允许一条流。"单飞"由客户端保证（M4）；服务端在 M0–M3 用 `pending` 行存在性做粗判即可，不引入 DO。

## 8. 主动唤醒

### 8.1 cron 技术约束【定】

- **Cron Triggers 先上，不碰 Durable Objects**。全局固定频率；条数上限是**平台级**的（Free 套餐 3 条），`wrangler` 的 schema 并不校验条数。
- **cron 时间是 UTC**：要"每天 6:30（Asia/Shanghai）建当天会话"，表达式是 `30 22 * * *`（前一天 22:30 UTC）。代码里统一用 `Asia/Shanghai` 常量换算，别散落魔数。
- 建议 3 条：
  1. `30 22 * * *` —— 建当天会话 + 生成前一天摘要
  2. `0 */2 * * *` —— 决策窗口（该不该开口）
  3. `30 3 * * *` —— 维护（衰减回写、孤儿扫描）
- **落地要改四处，缺一不可【定】**（已核对：Nitro 只写 `compatibility_date`/`main`/`assets`/`name`/compat flags，**从不生成 `triggers.crons`**）：
  1. `nuxt.config.ts`：`nitro.experimental.tasks = true`
  2. `server/tasks/<name>.ts`：定义任务
  3. `nuxt.config.ts`：`nitro.scheduledTasks: { '<cron 表达式>': '<task 名>' }`
  4. 根 `wrangler.jsonc`：`triggers.crons: [...]`，手写
  > **不要写 `export default { scheduled }`**：该 preset 的 Worker 入口自己拥有 `scheduled`，会按 `controller.cron` 转发到 `runCronTasks`。
- **DO Alarms 的时机**：等确实需要"每个未闭合事件单独定时"（"他说 3 点开会，3 点 10 分唤醒看看开完没有"）再说。那时每个对话对象可有自己的 alarm。

### 8.2 cron 的产物是"决策"，不是"消息"【定】

```text
收集信号（现在几点 / 距上次对话多久 / 未闭合事件 / 今日已开口次数）
        ↓
判断该不该说话、说什么
        ↓
该说才写 messages（source=proactive）；否则结束，什么都没发生
```

**大部分时候什么都不做。**

### 8.3 打扰预算【建议】

前稿只有"默认静默"，没给上限，容易变成每天几十条。补：

- 安静时段：**23:00–08:00（Asia/Shanghai）绝不主动**
- 最小间隔：两次主动 ≥ 3 小时
- 每日上限：**1–2 条**，超出即静默
- 优先级：未闭合事件到期 > 久未联系 > 时间节点

### 8.4 推送

客户端是 Kotlin（Android + Desktop），据此收口【建议】：

- **Android 走 FCM**（HTTP v1；Workers 侧需要 service account 的 RS256 JWT 换 access token，token 要缓存）
- **Desktop 不走推送**，靠前台轮询
- **原稿的 iOS/PWA + Web Push/VAPID 分支整体删除** —— 目标客户端是原生 App，不存在"添加到主屏幕"的前置条件
- 设备登记需要 `devices` 表（3.1 已补）
- **FCM 提前到 M3 而非 M4**：轮询意味着"不打开 App 就收不到"，主动找人的体验直接打折

## 附录 C：实现机制核对表

本文提到的每个"外部机制"都在**已安装版本**里核对过，不是凭记忆写的。核对版本：`ai@7.0.154`、`@ai-sdk/openai-compatible@3.0.79`、`nitropack@2.13.5`、`drizzle-orm@0.45.4`、`wrangler@4.153.0`。

| 机制 | 结论 | 注意 |
| --- | --- | --- |
| `streamText` 的 `abortSignal` / `onError` / `onAbort` | 均存在 | `onAbort` 能拿到 `{ callId, steps, reason }` |
| `onFinish` | **已 deprecated**，是 `onEnd` 的别名 | 一律写 `onEnd` |
| `onEnd` 载荷 | `text`（仅末步）、聚合 `usage`/`totalUsage`、`finishReason`、`steps`、`responseMessages` | 正好够填 `usage_json` / `parts_json` |
| `result.consumeStream()` | 存在 | 断线续写的关键；配合 `event.waitUntil(...)` |
| `toTextStreamResponse()` | 存在但 **deprecated** | 改用 `createTextStreamResponse({ stream })` |
| `waitUntil` 在 Workers 上的拿法 | `event.waitUntil(promise)` | 由 preset 的 module-handler 注入；另有 `event.context.cloudflare.context.waitUntil` |
| Nitro cron | 支持 `experimental.tasks` + `server/tasks/*` + `scheduledTasks` | **`triggers.crons` 不会自动生成**，必须手写进 `wrangler.jsonc` |
| `triggers.crons` | `string[]`，schema **无 maxItems** | 条数上限在平台侧；cron 按 UTC 执行 |
| `uniqueIndex` / `onConflictDoNothing` | 均可用 | `import { uniqueIndex } from 'drizzle-orm/sqlite-core'`；D1 driver 共用同一 insert builder |
| `text('x', { mode: 'json' }).$type<T>()` | 支持 | 物理类型仍是 `text`，写入 `JSON.stringify`、读出 `JSON.parse` |
| 流式 usage | **默认不返回** | 必须 `createOpenAICompatible({ ..., includeUsage: true })`，否则 `usage_json` 永远为空 |
